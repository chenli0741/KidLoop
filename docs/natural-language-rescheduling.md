# KidLoop 自然语言联动重排需求

日期：2026-09-08

状态：需求交接文档，尚未代表功能已实现。供新的实施对话使用。

> 2026-09-08 用户补充确认：没有班级需求，业务规则全部沿用现有系统。下文原始交接内容涉及班级或新增规则、参数的部分不再作为实施要求；开发以 [1.0 开发需求文档](natural-language-rescheduling-v1.md) 为准。

## 1. 目标与边界

用户通过文字或语音描述临时变化，系统理解变化范围，基于真实运营数据重新组合学生、线路、车辆和司机，给出能够执行的新排班及调整说明。

核心价值是解决复杂关系变化造成的连锁排班冲突。单个学生请假、标记缺席等已有简单操作不是本功能的优先场景。

当前业务量较小、规则相对简单，采用 KidLoop 后台专用的轻量排班模块，第一版不建设通用大型调度平台，不承诺全局最优。

## 2. 典型场景

运营人员输入：“这周 A 学校的 K 班十二点放学，其他年级照常。帮我重新排一下，尽量不要增加司机。”

实际运营中，一个司机常连续执行两条或多条线路，时间安排紧密。同一学校的学生可能按班级或年级分批放学；不同学校的学生组可能需要交叉组合接送。某一批学生时间变化后，可能影响该司机后续任务，再影响其他司机和车辆的安排。

系统需要识别受影响任务，尝试改变顺序、拆分或合并学生组、调整司机和车辆、重新组合跨学校线路；必要时提出临时线路和临时司机需求。

上述学校、人数和时间都是场景示例，实施和验证应使用用户确认的真实业务案例，不能把口述中不完整的人数当作配置。

## 3. 用户流程

1. 用户输入变化和偏好，语音先转成文字，两种输入共用同一处理流程。
2. 系统解析学校、班级或年级、学生范围、具体日期、时间变化、资源偏好和锁定条件。
3. 通过真实数据查询匹配对象；存在重名、日期范围不清或关键条件缺失时进行针对性追问。
4. 基于原排班生成试算草案，查找直接及后续受影响的任务，必要时扩大调整范围。
5. 展示候选方案、原安排与新安排对照、冲突及资源缺口。
6. 用户可以补充约束，例如“王司机第二趟不能动”，再试算。
7. 用户选定并确认后，后台重新校验当前数据并保存；若原排班已经被其他操作改变，应提示重新试算。

试算不得直接覆盖已发布排班。临时变更应限于确认的日期范围，不能自动改写长期常规安排。

## 4. 排班数据和规则

需要支持的业务结构：

- 同一学校按班级、年级或明确的学生组设置不同放学和可接时间。
- 一位司机在一天内连续执行多趟任务。
- 一趟线路可以包含多个学校或停靠点，记录接送顺序。
- 车辆座位数、司机和车辆可用时段、学生目的地。
- 站点之间的行驶时间、接学生及送达交接时间、必要缓冲。
- 临时司机和临时线路，以及用户锁定的任务。

硬性校验包括：学生安排完整且不重复、每段乘车人数不超载、司机和车辆任务不冲突、上一任务结束后能实际赶到下一站、满足接送时间窗口和资源可用条件、遵守锁定安排。

优化偏好包括：优先使用现有人车、尽量少改原排班、减少不必要的车程和等待。偏好的优先级需要在实施阶段明确；不能为满足偏好而突破硬性条件。

行驶时间来源、可接时间窗口、每站交接时长和缓冲余量需要从现有数据及运营经验核实，不凭空填写。模型不能自行编造司机、车辆或车程。

## 5. 后台排班模块

第一版采用 TypeScript 实现专用规则校验与有限范围的方案搜索，作为现有 Node.js / Next.js 后台的一部分；具体执行方式结合当前部署限制决定。

以原排班为起点，优先尝试受影响任务的局部调整。如果冲突传递到其他任务，则逐步扩大范围。尝试换顺序、换资源、拆分或合并学生组，必要时纳入已确认可用的临时资源。

返回可通过规则校验的候选方案、变化明细及解释依据。不得把“有限搜索内未找到可行方案”等同于“数学上证明无解”。只有有明确依据时才断言运力不足，否则说明搜索范围、未解决冲突和待确认条件。

应限制搜索时间与候选数量，具体阈值通过真实案例验证确定。后台内部试算多种组合不调用模型逐一决策。

## 6. AI 与后台的技术分工

流程：自然语言输入 → KidLoop 服务端调用 OpenAI API → 模型请求工具调用 → 后台执行查询或试算 → 返回精简结果 → 模型解释方案 → 用户确认 → 后台校验并保存。

模型负责理解需求、请求必要查询、生成结构化参数、解释冲突和候选方案。后台负责权限检查、对象匹配结果验证、数据读取、排班计算、业务校验和数据库写入。

工具调用传递的是预先定义的功能名称和参数，不生成并执行任意脚本。模型提出调用请求，由 KidLoop 后台验证并实际执行。

建议工具边界，名称可按项目惯例调整：

- 查询相关学校、学生组、排班及资源。
- 根据结构化变更和约束试算排班。
- 根据草案 ID 查询候选方案及变更详情。
- 在用户明确确认后提交指定草案。

查询和变更必须遵守当前用户的角色与组织权限。API 密钥只保存在服务端。提交需要防重复、检查数据版本，并保留原安排、变更结果、操作者和时间。

## 7. 方案展示

展示司机完整任务时间线及变更前后对照，包括学生换车、司机换线路、出发或到达时间变化、新增线路和临时司机需求。

说明调整原因，例如前一趟送达加转场时间导致无法按时到达下一学校。对于无法排开的部分，列明受影响学生组、时段、区域、人数及缺失条件。

界面支持继续追加约束、锁定安排、重新试算及确认应用。界面和模型解释支持简体中文、英文，默认中文。iPhone 内的链接、预览和返回行为遵守 AGENTS.md 的 App 内跳转规范。

## 8. Token 与成本要求

后台排班搜索本身不消耗模型 token，但仍有普通服务器计算成本。模型调用的输入包括规则、工具定义、相关数据、对话及工具结果；输出包括工具参数和解释，所选模型还可能产生推理 token。

尽量只向模型提供相关日期、学校和资源的数据。不提供无关学生照片、家长联系信息、全库数据或完整搜索过程。后台完成组合搜索，仅返回候选方案及冲突摘要；控制对话历史、工具结果大小和调用轮数。

信息完整时以较少调用完成一次任务，之前讨论的“两三次请求”和“累计几千到一两万 token”只是初步预算假设，不是验收指标、实测值或成本承诺。

按一次完整重排任务汇总所有模型请求，记录模型、调用次数、输入、缓存输入、输出及可获得的推理用量、耗时和费用估算。避免重复计算模型已经包含在输出用量中的推理 token。费用按实施时核实的对应模型价格计算；语音转写费用单独统计。

上线前使用真实代表性案例测量单次重排总费用和效果，再确定模型、调用限制及预算策略。不得用当前 Codex 会话用量代替未来产品 API 的成本估算。

## 9. 验收场景

1. 某学校某年级仅本周提前放学，其他日期的常规计划保持不变。
2. 同一司机连续两趟因变化产生转场冲突，系统发现并联动调整。
3. 两个学校分批放学，可通过重新组合线路使用现有运力完成。
4. 现有运力未找到可行方案，系统明确报告未解决条件，并可纳入临时司机重新试算。
5. 锁定某司机的一趟任务后，任何方案都不修改该任务。
6. 不生成超载、重复安排学生、遗漏受影响学生或时间不可执行的方案。
7. 试算期间不写正式排班；确认时遇到并发修改不能覆盖新数据，重复提交不产生重复行程。
8. 同一结构化请求经文字或语音输入，使用同一排班流程；对象不明确时追问。
9. 每次完整任务有可核对的模型用量与成本记录。

## 10. 新对话实施起点

先阅读 AGENTS.md、PROJECT_OVERVIEW.md、docs/architecture.md、当前数据库结构和排班实现，核对支持多停靠点、分批放学、连续任务和权限控制所需的差距，再确定最小可实施范围。

推荐先建立结构化重排请求、规则校验和草案试算，用一个真实复杂调整案例跑通；再接入模型工具调用及自然语言交互，语音转写复用文字流程。实现顺序不表示可以省略最终自然语言入口。
