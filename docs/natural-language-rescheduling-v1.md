# 自然语言驱动的接送排班联动调整 — 1.0 开发需求文档

版本：1.0 草案

日期：2026-09-08

状态：开发需求基线；已落地代码及当前限制见 [实现与验证记录](rescheduling-implementation.md)，不代表已经部署或完成真实运营验收。

## 1. 已确认边界

- 没有班级需求：不按班级解析、筛选、分组或配置排班。
- 所有业务规则沿用当前系统，不新增接送规则、时间窗口、车程参数、资源规则或优化权重配置。
- 本功能增加自然语言理解、现有排班的联动试算、方案展示、确认和保存能力。
- 现有规则的含义不因 AI 介入而改变。试算与保存必须使用同一套现有业务规则。

依据：[项目总览](../PROJECT_OVERVIEW.md)、[已确认需求](confirmed-requirements.md)、[架构](architecture.md)、[原始交接稿](natural-language-rescheduling.md)及当前代码。原始交接稿中涉及班级或新增规则、参数的内容，以本次用户确认及本文件为准。

## 2. 目标

管理员用自然语言描述临时变化，系统读取真实数据，找到受影响的学生、线路、司机及车辆，联动调整相关安排，展示方案。管理员确认后，新安排仅在指定日期生效。

继续保持现有流程：学校规则 → 固定多站线路 → 固定司机、车辆和学生 → 自动每日任务 → 接送状态。无需每天重新排班。

示例：“这周 A 学校的 K 年级十二点放学，其他年级照常。帮我重新排一下，尽量不要增加司机。”其中名称和时间仅用于说明，不是实际配置。

| 领域 | 沿用现有能力 | 本次增加 |
| --- | --- | --- |

## 4. 1.0 功能范围

### 4.1 输入与理解

- 支持文字输入和语音转文字；转写内容可修改，两种输入共用后续流程。
- 识别日期、学校、年级、明确学生名单、时间变化、指定人车及用户要求。
- 相对日期按洛杉矶运营时区解析，在确认前展示具体日期及实际适用日。
- 对重名、范围不清或缺少关键输入进行针对性追问，不猜测真实对象。
- 用户说“尽量不要增加司机”时作为本次试算偏好；说“这趟不能动”时作为本次调整边界，不新增长期业务规则配置。

### 4.2 联动试算

以当前安排为起点，查询直接受影响线路，以及共享司机、车辆或学生的关联任务。优先局部调整，冲突传递时逐步扩大范围。

支持在现有业务模型内尝试：调整站点时间和顺序、更换已有可用司机车辆、拆分或合并学生安排、重新组合跨学校线路，以及生成限定日期的临时线路方案。

使用真实记录，不编造人车、学生、地点或行驶时间。不接入新的地图耗时计算，也不要求管理员增加一套规则参数。现有时间信息不足以判断的事项，应明确说明，不能声称已经完成实际转场可达性验证。

后台负责有限范围的组合搜索，模型不逐个决定组合是否合法。搜索无结果时说明“当前搜索范围内未找到符合现有规则的方案”，不能断言数学上无解。

### 4.3 方案与确认

- 展示原安排和新安排，包括日期、线路、学生、人车、站序及时间变化。
- 展示司机相关任务时间线，说明为什么需要联动调整。
- 显示通过的现有规则校验、尚未解决的冲突及无法判定的事项。
- 用户可继续补充限制后重新试算，或者放弃草案。
- 用户明确选择方案并点击确认后才修改业务数据。
- 存在未解决的现有规则冲突时不允许应用。

## 5. 必须保持的现有业务边界

| 现有规则 | 联动调整要求 |
| --- | --- |
| 学校学期、星期、校历与年级时间 | 使用现有解析逻辑；日程只覆盖已有上课安排，不自动增加原本没有接送的日期 |
| 学生每周不接送及家长请假 | 沿用现有排除和状态处理，不因重新安排而恢复接送 |
| 学生上下车站 | 保持有效学校上车点及后续下车点，默认保留原目的地 |
| 每段容量 | 沿用分段在车人数计算，不以整条线路总人数替代 |
| 人车与学生冲突 | 复用当前校验，检查调整后的整体安排及范围外关联任务 |
| 临时线路优先替代 | 只替代适用日期的所选学生，长期固定名单保持不变 |
| 已执行保护 | 不重写已开始或明确完成的任务，不丢失操作历史和家长请假事实 |
| 临时结束、停用或不可用 | 沿用现有恢复未开始原安排及冲突提示逻辑，不另设恢复规则 |
| 当前运营学期 | 不修改存档历史，不把本次临时安排复制到下一学期 |
| 角色权限 | 管理员试算和提交；司机、家长沿用现有数据访问范围 |

若复用时发现现有规则无法表达某种请求，应在草案中说明该请求暂不支持，不自行扩展业务规则。

## 6. 数据与保存方案

本节为技术实现建议，不增加业务规则或另一套正式排班。

### 6.1 草案

保存调整请求、结构化输入、试算版本、关联数据版本、候选方案和差异说明。试算只写草案数据，不修改学校规则、线路或每日任务。

未来尚未生成的任务应使用无业务写入副作用的计划推导。不能直接调用会生成正式任务的读取流程作为试算步骤。

### 6.2 正式应用

优先复用学校日历日程与临时线路机制表达变化。联动涉及多条线路时，作为一个整体方案进行校验和事务保存，不能逐条保存后留下中间冲突。

保存前重新读取并核对相关校历、线路、学生安排、人车和执行状态，包括试算后新增的冲突记录。数据改变时拒绝旧草案并提示重新试算，不覆盖别人的新安排。

同一事务保存必要的学校日历日程变更、临时线路安排、关联任务同步和审计。任何一步失败整体回滚；重复提交返回同一次应用结果。

接入现有 `materializeRoutes` 生成链路。管理员、司机或家长后续读取以及未来日期首次生成时，均须保持已确认结果。不能只修改 `trips` 后被原固定线路重新覆盖。

如果现有存储结构需要技术扩展，只补充实现上述既有业务语义所需的数据，不引入新的优先级或恢复规则。保留学生关联、家长请假和状态历史。

### 6.3 审计

记录原请求、最终确认方案、调整日期、前后安排、操作者、提交时间及幂等标识。恢复或再次修改仍通过既有校验，不删除历史事实。

## 7. AI 与服务端分工

流程：自然语言 → 服务端 OpenAI API → 受控查询及试算工具 → 候选和解释 → 用户确认 → 后台校验保存。

模型负责理解、结构化参数和解释；后台负责权限、真实查询、排班搜索、业务校验及写入。工具采用固定参数结构，不接受任意 SQL 或脚本。模型不能自行确认或提交方案。

API 密钥只在服务端保存。模型仅接收相关日期和对象的必要信息，不发送无关照片、家长联系方式或全量数据。

模型调用及搜索不持有数据库长事务；搜索时间、候选数量和调用次数设置技术上限，具体值通过案例验证确定。若部署执行预算不足，使用可持久化、可查询状态的作业机制。

记录完整请求的模型、调用次数、输入、缓存输入、输出、可取得的推理用量、耗时及费用估算，失败重试也归集。避免重复计算已包含在输出中的推理 token；语音费用单列。具体模型和价格实施时核实，不作固定 token 或费用承诺。

## 8. 界面

桌面端提供输入与条件摘要、候选比较、司机时间线和学生变化明细。iPhone 采用输入、核对、查看方案、确认的分步布局，不直接缩小桌面表格。

状态包括：待补充、试算中、待确认、未找到方案、草案已过期、应用中、已应用及失败。网络中断后允许查询提交结果，不能把超时直接显示为已失败或已成功。

简体中文默认，支持英文。沿用现有页面读取和刷新机制；“已应用”不代表已发送推送或司机已阅读。

所有站内链接、外链、地图和预览留在 App 内并可返回或关闭。验收覆盖普通链接、`target="_blank"`、`window.open`及重定向，包含 iPhone App 实际流程。

## 9. 开发顺序

| 阶段 | 交付和完成条件 |
| --- | --- |
| 1. 现有规则复用 | 梳理并复用当前排班推导与校验，形成无业务写入副作用的试算入口 |
| 2. 联动搜索 | 结构化变化可生成符合现有规则的候选，或返回具体冲突 |
| 3. 保存闭环 | 草案、版本复核、批量事务、幂等、审计和每日生成衔接通过验证 |
| 4. 自然语言交互 | 文字、语音、追问、方案解释、两端布局和中英文完成 |
| 5. 验收 | 代表性真实案例、回归测试、iPhone 操作和用量记录完成，更新实施状态 |

以上是开发顺序，最终交付不能省略自然语言入口。正式编码前阅读 AGENTS.md 及当前 Next.js 随包相关文档。需求整理阶段仅编写文档；后续开发与验证记录单独维护。

## 10. 验收标准

| 场景 | 通过标准 |
| --- | --- |
| 某学校某年级本周改时 | 精确影响指定日期和年级，其余安排按现有规则保持 |
| 模糊名称或日期 | 追问并显示实际匹配对象，不擅自扩大范围 |
| 关联司机连续多趟 | 纳入关联任务试算，检出现有规则定义的冲突；不虚报车程验证 |
| 多校学生重组 | 站序、上下车关系、分段容量及资源冲突均通过现有校验 |
| 用户限定某趟不变 | 候选不修改该趟，仍检查与它相关的任务 |
| 现有条件下暂无方案 | 返回冲突和搜索边界，不编造资源或修改规则 |
| 学生请假或每周不接送 | 排除及状态处理与当前流程一致 |
| 试算、追问或放弃 | 不改变正式校历、线路和任务 |
| 确认前出现新修改或司机操作 | 旧方案被拒绝，不覆盖最新数据和执行事实 |
| 重试及保存失败 | 幂等生效；失败整体回滚，无部分应用 |
| 应用后刷新和未来任务生成 | 各角色读取结果一致，不恢复旧方案、不重复学生 |
| 既有临时线路交叉、到期、停用 | 沿用现有替代、恢复和冲突规则 |
| 文字与语音、中英文 | 同一含义进入同一结构化排班流程 |
| iPhone 实际使用 | 输入、对照、确认、打开链接及返回可用，均留在 App 内 |
| 用量审计 | 一次调整的所有模型调用可核对，语音单列，无重复计费统计 |

测试使用隔离数据；运营效果以用户确认的真实案例验证。未完成的实机或运营验证必须明确记录，不能用桌面测试替代。
